**问：** 什么是 Prompt 工程？

> 就是怎么写好给模型的提示词。

**问：** 你设计 Prompt 的核心原则是什么？

> 清晰：把任务背景、目标、边界和输出要求讲清楚；结构化：把角色、指令、上下文、示例、格式约束等尽可能的拆开组织。

**问：** 什么是 Harness 工程？

> 这个说的是把大模型"武装"起来、架起来干活的那套系统。比如你写的 Agent，它得能调用工具、能读写文件、能连数据库、能调用别的 API，还能把任务拆成几步、一步步跑，中途出错还能重试，最后把结果拼起来。Herness 是这些把这套流程串起来的"外骨骼"。

**问：** 是说 Agent 是 Harness 工程的产物？

> 没错，Harness 就像一套乐高积木和说明书，Agent 就是拿这套乐高搭出来的那个机器人。Harness 是手段和系统，Agent 是结果和实体。

**问：** Prompt 工程和 Harness 工程的区别？

> 模型就像一台发动机，Prompt 是你怎么踩油门、怎么操作它；Harness 就是把它装进车架、接上方向盘、油箱、传动轴，让它能真正开起来上路。一个是会"说话"，一个是会"干活"。

**问：** 什么是大语言模型，LLM 的本质是什么？

> 说白了就是一个特别大的神经网络，专门用来处理文字、图片这类东西。你给它输入，它就输出，中间是靠一堆海量数据训练出来的。它的本质就是一个概率模型（预测）。

**问：** LLM 和 NLP 模型有什么区别？

> LLM 是一个用海量无标注数据训练出来、靠"预测下一个词"学会语言规律和知识的超大神经网络；传统 NLP 模型是为单个特定任务专门训练的、小而专的模型。LLM 通用、能通吃多任务、靠 prompt 引导、基本不需要特征工程；传统 NLP 专用、一个模型对应一个任务、需要大量标注数据、依赖人工特征和规则。

**问：** 说说你理解的 Agent 是什么？

> Agent 是以 LLM 为核心，具备规划（Planning）、记忆（Memory）和工具调用（Tool Use）能力，能够自主拆解复杂任务、循环执行、感知反馈并持续推进任务直到完成自主实现任务闭环的智能体，实现从"文本生成"到"任务自主执行"，不再只是被动响应指令，而是能像员工一样，你给个目标，他自己想办法、自己动手、自己交差。

**问：** 既然大模型已经这么强了，为什么还要做 Agent？

> 大模型强是强在"会说话"，但很多活儿光"会说话"干不成，得"能动手、能连着干"。它俩不是替代关系，是配合关系——模型当脑子，Agent 当手脚和管家，能把模型那种"强"真正"落地"。

**问：** 那 Agent 和单纯的 LLM 接口调用（chat）有什么区别？

> Chat 是"你问它答"，模型只负责说话；Agent 是"你给它目标，它自己动脑子调工具、循环执行、把事儿办成"。 核心区别就是"能不能动手、能不能自己循环推进"。你加个循环、加个工具调用，Chat 就慢慢变成 Agent 了。

**问：** 说到循环，Agent 如果在执行中陷入死循环怎么办？

> 先设最大轮数和超时拦住它，再用重复检测发现它卡壳，最后给它一个"干不成算了"的兜底。

**问：** 如果让你设计一个 Agent，你会怎么设计？

> 模型是"脑"，工具是"手"，循环编排是"腿"，记忆是"记事本"。 这四块拼起来，再配上一条主线：给目标 → 模型规划 → 调工具干 → 看结果 → 攒记忆 → 再规划 → 直到办成或兜底退出。

**问：** 你提到了记忆，Agent 的记忆系统是什么？短期和长期记忆方案怎么设计？

> 短期记忆像你这次开会随口记的便签，开完就散了；长期记忆像你脑子里存下来的经验和笔记，是积累的、能随时翻出来的"档案库"。核心就是——短期用上下文存，长期用数据库 + 检索（向量）来取，而且只存有长期价值的东西。

**问：** 你说短期记忆用上下文存，那短期记忆过长超过 token 限制怎么办？

> 裁剪掉没用的、压缩成摘要、把重点状态外置存储，然后只把当前这步需要的、捞回来喂给模型。在实际项目里最常用的是摘要压缩和滑动窗口，而且经常组合用，滑动窗口丢弃前先做一次摘要，尽量不丢重要信息。

**问：** 如果 Agent 调工具失败怎么办?

> 我的思路是分级容错，别一失败就整个崩掉。先分清哪类失败，能重试的就带退避重试，参数错了就喂回错误让模型自我修正，实在不行用替代方案降级，最后都不行就停下来把情况说清楚。核心是允许失败、留兜底、不崩。

**问：** 那如果 Agent 的执行结果不稳定呢？

> 一是把能固定的都固定（结构化、写死规则），二是加校验不轻信输出，三是关键判断多采样求稳，四是设底线和置信度，五是留降级兜底，六是记录监控持续优化。靠流程和约束把它稳稳托住。

**问：** 你怎么证明新版 Agent 比上个版本的效果更好？

> 先定好量化指标，再用同一套固定测试集让新旧版本对跑，关键任务加人工盲评，同时对比稳定性和边界表现，再做回归确认没退化，有条件就 A/B 实测。用数据和对比说话。

**问：** 之前很火的 OpenClaw 算 Agent 吗？

> 当然 算，OpenClaw 就是一个独立的、贴身帮你办事的个人智能体，就是"你请的那个能干的助理"。

**问：** 那 Hermes 呢？

> 它不是 Agent，Hermes 是一个"平台 / 底座"，它是让你能搭出、并运行一大堆 Agent 的那套环境，是"能养一堆助理、还给它们发活、管它们干活的办公室"。

**问：** 刚才说了这么多"手搓 Agent"，你知道有哪些成熟的框架吗？

> 我用的最多的还是 LangChain、LangGraph。

**问：** LangChain 和LangGraph 有什么区别？

> LangChain 提供"拼 LLM 应用的零件和能力"，LangGraph 用它来"编排一个复杂、有状态、能循环的 Agent 流程"。前者是工具箱，后者是施工图纸和流程，LangGraph 经常把 LangChain 的东西当成自己的节点来用。 我的 multi-agent-core 就是基于 LangGraph 搭建的用于编排复杂的多智能体流程的核心包。

**问：** 谈你谈对 LangChain 中核心概念「Chain」的理解。

> Chain 就是把多个"组件"按顺序串起来，形成一条处理链路。它本质上是把 LLM 应用拆成一个个可复用的"环节"，再把这些环节串成一整条流水线。你输入一个东西，它顺着链一步步往下走，每一步做一件事，最后输出结果。

**问：** 你再讲讲它的核心作用与设计理念。

> 分而治之 + 组合复用，作用是"把繁琐的粘合逻辑收敛成可复用、可替换、数据流清晰的链路"。

**问：** 你了解 LangChain 的底层架构与实现原理吗？

> LangChain 的底层架构核心是"Runnable 统一协议 + 组合复用 + 接口抽象"。它通过让所有组件都实现 invoke/stream/batch 这套协议，实现"任意组件可串联、可嵌套、可替换"；通过管道符把 Runnable 串成 chain，实现数据流从上往下传；通过接口抽象实现厂商无关。这套"统一接口 + 组合"的设计，正是它能拼出各种 LLM 应用、也是 LangGraph 能在它之上做图编排的根本。

**问：** 那使用 LangChain 构建 Agent 的核心步骤是什么？

> 现在都直接用LangChain V1 的 create_agent(model, tools, system_prompt) → compile(checkpointer) → astream 就能跑起来。核心是它内部自动帮你跑那个"决策→调工具→反馈→再决策"的循环，当前版本已经不用手写了。如果要更精细的控制（比如多智能体、子代理、中间件、人机确认），就在 create_agent 基础上加 middleware、subagents，或者自己用 StateGraph 搭一个图。

**问：** LangChain 是如何实现记忆的（短期）？

> 核心机制是对话消息放在图状态（state）的 messages 字段里，每一轮对话都往这个 messages 里追加。这样模型每次都能看到"之前聊了啥"，这就是短期记忆；持久化靠 checkpointer：你给 compile 一个检查点器（内存的 InMemorySaver、或 SQLite/MySQL/Postgres 的），它会把每一轮的状态快照（包括 messages）存下来。下次同一个 thread_id 再进来，它就自动把历史消息捞出来加载；跨会话/跨线程：用 thread_id 区分不同会话。同一个 thread 共享记忆，不同 thread 独立。这就实现了"短期记忆的自然延续"。

**问：** 聊聊你这个 multi-agent-core 吧，这个是什么背景？

> 为了让业务方不用碰 LangGraph 细节就能搭 Agent，避免重复造轮子。

**问：** 你既支持 Skill 又支持 MCP，它们不都是工具？有何区别？

> MCP 是"连外面的世界"（接外部系统、数据源，用统一协议），Skill 是"用我自己的本事"（封装好的、可复用的做事脚本，沙箱里跑）。一个是标准化外部接口，一个是内置可复用能力。MCP 相当于你给 Agent"配了好多不同公司的电话"，要查哪个公司就打哪个；Skill 相当于你给 Agent"一本写好的操作手册"，遇到某类活儿就照着手册办。所以它俩不是同一个东西的重复，而是互补的——MCP 解决"够得着外部"，Skill 解决"有一套现成方法"。

**问：** 你说 MCP 是标准化外部接口，但是我的业务系统已经有现成的 API 了，为什么还需要 MCP？

> API 是已经存在的能力，MCP 是"把这些能力以模型能理解、能自主调用、还能统一管理的方式，标准地暴露出去"。核心不是"API 有没有"，而是"模型怎么规范、高效地用上它们"。接口简单就自己写工具，接口复杂/多/要复用，就值得包成 MCP。

**问：** 那 MCP 的安全机制你如何保障？

> 最小化暴露（默认关闭）、细粒度鉴权、输入校验与危险操作过滤、沙箱隔离，再加一层审计监控兜底。

**问：** 你在编排框架中也内置了一些工具（check_file_exist）这些工具和 MCP、Skill 又有何区别呢？

> 属于内置工具，用 @tool 把一个 Python 函数注册成"工具"，模型通过 Function Calling 来调用它；MCP 是和 LLM 无关的外部标准协议，不同的 AI 应用都可以接入相同的 MCP。

**问：** 你的核心包叫 multi-agent-core，那你解释一下什么是 Multi-Agent？

> Multi-Agent 不是"多个模型在一起瞎聊"，而是把复杂任务拆给多个有明确职责的专业智能体，通过编排让它们分工协作、互相传递结果，共同把任务办成。

**问：** 你的 Single-Agent 既然已经支持了 Skill、MCP、Tools 能力这么强了，什么时候需要 Multi-Agent？

> 单 Agent 负责"把简单/中度任务干好"，Multi-Agent 负责"复杂、多角色、可并行、需要审查制衡、需要好维护"的任务。判断标准就一条——任务复杂到单 Agent 干不动、干不稳、或干得不好管理了，才值得拆。该拆就拆，不该拆就单干。

**问：** 我看你还支持了 deepagents，什么是 deepagents？

> DeepAgents 是 LangChain 的开源 Agent 装配库，也就是"能规划、能用子代理、能操作文件系统的 agent"。本质是 create_agent（原生）+ 一堆 middleware + backends + profiles 的高层装配。

**问：** 介绍一下 Workflow、Agent、Tools 这三个的概念和区别？

> Workflow 搭好骨架，Agent 在关键节点自主决策，Agent 决策后再调 Tools 落地执行。如果是提前写死、按图执行 → Workflow；如果是模型现场决定、自己推进 → Agent；如果就是一件具体的、被调用的动手能力 → Tools。

**问：** 说说什么是 RAG？

> RAG 就是检索增强生成。先让模型去搜相关资料，再把搜到的资料喂给它，让它基于这些资料回答。

**问：** 能否描述一个完整 RAG 系统的详细工作流程？

> 离线（建库）：采集 → 解析清洗 → 切块 → 向量化 → 存向量库；在线（查询）：查询理解（改写/补全）→ 向量召回 → 重排 → 组装上下文（拼 prompt）→ LLM 生成 → 后处理（校验/格式/防幻觉）→ 输出 + 反馈优化。

**问：** LLM 主要使用 RAG 来解决什么问题？

> RAG 主要解决模型因为知识受限导致的"瞎编（幻觉）"和"不知道最新/私有知识"。本质上它让模型"别凭空说，先去查资料再答"，既准又能追溯，还不用重训模型，改知识库就行。

**问：** 相比直接微调 LLM，RAG 解决了什么问题？微调和 RAG 各自的优劣势是什么？

> RAG 相比微调，主要解决了"知识更新贵且过时、不可溯源"的问题——外部知识库现取现用、可追踪、改了库就改答案。微调强在"注入内在能力/风格/领域规则"，RAG 强在"接入实时、私有、可溯源的知识"。微调是"让模型会"，RAG 是"让模型有料"，优先补知识用 RAG，要改能力/风格用微调，需要时两者结合。

**问：** RAG 与 Agent 自主文件检索应该如何选型？

> RAG 适合"知识已整理好、问题明确、要稳定可控可溯源"的场景；Agent 自主检索适合"信息散、不确定、需要探索性多步骤查找"的场景。总之能 RAG 就 RAG（稳），RAG 搞不定、确实需要灵活探索，再上 Agent。

**问：** 能否介绍一下向量检索和关键词检索的区别？

> 关键词检索按"词一样不一样"匹配，快准、懂术语，但不懂语义；向量检索按"意思一样不一样"匹配，懂同义、懂上下文，但对精确词偏弱且更贵。一般关键词 + 向量混用（再加重排）结合使用。

**问：** 那你一般怎么润色用户的 Query？目的是什么？

> 常用做法是改写+口语化、多轮上下文补全、复合问题拆解、关键词/同义扩展。核心原则是去掉噪音、突显意图、补全上下文、但绝不改变用户本意。目的是让用户的原始问题，变成一个更明确、更完整、更适合去检索的表达，从而提升召回准确率。

**问：** 那你了解多路召回吗？

> 多路召回是同时用多种检索通道（向量、关键词、元数据/标签等）去捞候选，把各路结果合并去重，目的是通过"多个通道互相补盲"来提高召回率、不漏掉相关结果。 它解决的是"捞得全"，真正的"筛得准"靠后面的重排。多路召回 + 重排是生产级检索系统的标准套路。

**问：** 你觉得 RAG 实际落地中最难的地方在哪？

> 最难的地方在于把"检索 + 生成"这套概率系统，调成"稳定可靠、可评估、可维护"的系统。因为 RAG 本质是"概率"的，检索会飘、模型会幻觉、评分难、数据又不干净，你要在产品上去搓稳定、可靠、可评估的一套东西。

**问：** 你们 RAG 知识库上线之后，文档更新了怎么办？

> 文档更新这件事，本质上就是维护"源 → 向量库"这条同步链的一致性，核心是保证任何时候库里都是"最新的、无冲突的、可追溯的"数据。

**问：** 那你们线上跑了 RAG，通常怎么衡量它的效果好不好？

> 衡量 RAG 好不好，我一般分两层：检索层（看 Recall/Precision，知识块召对没）、生成层（看忠实度/相关性/引用，答案准不准）；手段是自动化（LLM 裁判打分）+ 人工精评 + 离线标准集回归；线上再加真实反馈（点击、投诉、兜底率）作最终检验。真正的关键是把这几套指标对齐，让离线分数能真实反映线上的好坏，这才是衡量 RAG 效果的完整闭环。

**问：** 如果你们线上的 RAG 回答不准你会从哪查？

> 按链路查。先看"检索捞对没"（没捞对就去查切块/query/向量/召回/数据），再看"答对没"（答错就去查提示词/上下文组装/模型）。很多"答不准"的根因，往往不是模型，而是检索或数据。排查的核心是把这条链打日志、逐环节看数据流动，定位到底是哪一环烂了。

**问：** 那如何规避 RAG 系统中大模型的幻觉呢？

> 最有效的是"提示词强约束 + 承认不知道 + 引用来源"，最根本的是"把知识库管好（覆盖全、数据准）"，最后一道防线是"生成后校验 + 引用核对 + 答不上就承认/兜底"，再配合降 temperature 和持续评估反馈。

**问：** 如果有不同来源的文档发生知识冲突时，RAG 应该信谁？

> 不是"选一个正确的"，而是"建立来源优先级（权威+时效）+ 识别冲突 + 呈现分歧 + 标注来源 + 兜底转人工"。 能靠规则定优先级的就定（官方/新的优先）；真分不清的，诚实告诉用户存在冲突，别硬编。最忌讳的就是自作主张、偷偷只信一个、还不告诉用户。
